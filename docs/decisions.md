## Phase 5 implementation decisions

| D-35 | **Tax = one pure calculator** (`src/server/tax/calculator.ts`), integer paise, half-up rounding (from `money.ts`). INCLUSIVE extracts the base (`taxable = round(gross*10000/(10000+rateBps))`, `tax = gross - taxable`) — never adds tax twice. CGST = `trunc(tax/2)`, SGST = `tax - CGST` (sums exactly); IGST for inter-state. STANDARD only; `SECOND_HAND_MARGIN` throws. | 2026-09-07 | Master §6. |
| D-36 | **Inventory services take a `Prisma.TransactionClient`; the caller owns the tx.** Conditional `UPDATE … WHERE onHandQty - reservedQty >= q` in deterministic variant order for atomic all-or-nothing; `FOR UPDATE` (+ `SKIP LOCKED` for the sweep) serialises expiry vs conversion. Every movement writes an `InventoryTransaction` with a unique idempotency key (`reserve:/release:/expire:/convert:/cod-alloc:/cod-cancel:/late-capture:`), so retries are no-ops. Provider calls stay outside the tx. | 2026-09-07 | Master §7; the Phase 2 `reservedQty <= onHandQty` CHECK is the backstop. |
| D-37 | **Quote is computed, not persisted.** `computeQuote` returns `expiresAt` + a sha256 `hash` over the normalised request + server totals. `placeOrder` recomputes; a stale `clientQuoteHash` → `PriceChangedError`. Client-sent prices/totals are never read. There is no `Quote` table. | 2026-09-07 | Master §6/§7.1; keeps the schema unchanged. |
| D-38 | **Checkout idempotency** via `CheckoutRequest @@unique([scope, idempotencyKey])` + `requestHash`. Same key + same hash → return the existing order; same key + different hash → `IdempotencyConflictError`. The row is claimed inside the placement tx (P2002 → a concurrent winner). `scope` = `customer:<id>` or `guest:<sha256(phone|email)>` (a candidate, not proof of ownership). | 2026-09-07 | Master §7.2. |
| D-39 | **Late capture** (`settleCapturedPayment`): convert on capture; if reservations are no longer ACTIVE, `reacquireForLateCapture`; on shortfall → order `NEEDS_REVIEW`, payment `PAID`, fulfillment blocked. A real payment is **never** recorded as failed. | 2026-09-07 | Master §7.7. |
| D-40 | **Shipping test adapter** (`src/server/shipping`) behind a typed `ShippingPort`; every response carries `testAdapter: true`. Phase 8 swaps Shiprocket in. | D-41 | **State machines** are explicit transition tables (`src/server/orders/state.ts`) with `assertTransition`; `deriveAggregatePaymentStatus` computes the order-level payment status from attempts + refunds so a failed later attempt cannot downgrade a captured one. `Order.version` optimistic-concurrency column is incremented on every lifecycle write. | 2026-09-07 | Master §8. |

## Phase 6 implementation decisions

| ID | Decision | Date | Reason |
| --- | --- | --- | --- |
| D-43 | **`.npmrc` `legacy-peer-deps=true` + `inngest` pinned to `3.54.2`.** `inngest@4.x`/latest `3.44.x` pulled an OpenTelemetry chain with a high-severity advisory and an ERESOLVE conflict (optional `@sveltejs/kit` peer → `@sveltejs/vite-plugin-svelte` wanting `vite@8` vs our `vite@7` from vitest). The peer is optional and unused. `3.54.2` → `npm audit` 0 vulnerabilities. | 2026-09-07 | Playbook Phase 6 needs a real scheduler; keep the dependency tree clean and the sveltekit peer out of the way. |
| D-44 | **Transactional outbox producer** (`src/server/events/emit.ts` `emitDomainEvent(tx, …)`). `DomainEvent` + `OutboxEvent` are written in the **same** `tx` as the state change. A committed change always has a `PENDING` outbox row; a rolled-back change leaves nothing. `place-order.ts` and `orders/lifecycle.ts` `timeline()` both go through it (replacing hand-rolled `tx.domainEvent.create` + `tx.outboxEvent.create` from Phase 5). | 2026-09-07 | Master §8 — "no event without its state change, no state change without its event". |
| D-45 | **Lease-based dispatcher** (`dispatcher.ts`). One SQL statement claims a bounded batch of fresh `PENDING` **and** stale `DISPATCHING` (lease expired) rows with `FOR UPDATE SKIP LOCKED`, sets `status=DISPATCHING`, `leaseOwner`, `leaseExpiresAt = now + leaseMs`, `attempts+1`, `RETURNING` joined to `DomainEvent`. Send to the transport; only on ack → `markDispatched` (updateMany guarded by `leaseOwner = owner`, so a worker that lost its lease cannot mark). Defaults: lease **30 s**, batch **50** (cap 200), **8** attempts, backoff base **2 s** full-jitter `2^(n-1)` capped 5 min. Exhaustion → `status=FAILED` + one `OperationalTask` `outbox:<id>`. **`DISPATCHED` ≠ effect done.** | 2026-09-07 | Master §8 — "bounded lease-based dispatcher"; consumers, not the dispatcher, guarantee exactly-once *effect*. |
| D-46 | **Durable consumer dedup** (`side-effects.ts` `runOnce`). Each consumer step has a stable `executionKey`; `runOnce` `create`s a `SideEffectExecution{status: RUNNING}` — P2002 means it already ran: `SUCCEEDED`/`RUNNING` → skip (`{ran:false}`), `FAILED` → flip back to `RUNNING` (attempts+1) and retry. Success stores `providerRef`; failure stores `lastError` and rethrows. This is what makes a redelivery (crash between send and mark, or Inngest's own retry) safe. | 2026-09-07 | Master §8 — "independently retryable consumers, persistent execution keys". |
| D-47 | **Operational tasks are dedup-keyed** (`operational-tasks.ts`). `openOperationalTask` upserts on `dedupeKey`; reopening sets `status=OPEN, resolvedAt=null`; `resolveOperationalTask` is `updateMany WHERE status=OPEN`. So retry storms, repeated health checks and repeated failures collapse to **one** row per logical problem (`outbox:<id>`, `outbox:health`, later `payment:<id>` etc.). | 2026-09-07 | Playbook Phase 6 — "exhausted jobs surface once". |
| D-48 | **Webhook inbox** (`src/server/webhooks/inbox.ts` `ingestWebhook`). Verify signature over the **raw** body first (throw `WebhookVerificationError` → 401, nothing persisted); then `create` a `WebhookEvent`; P2002 on `(provider, externalEventId)` → `{isNew:false}` return the stored row (idempotent redelivery); any other error rethrows → 5xx so the provider retries. Processing is separate (`markWebhookProcessed`/`markWebhookFailed`). `ReconcilePort` interface defined for Phase 7–8 pollers. | 2026-09-07 | Master §8 / §7.6 — "persist webhooks before acknowledgment; a verified-but-unpersisted event is never acted on". |
| D-49 | **Recurring work runs as real Inngest schedules** (`src/inngest/functions.ts`, served at `/api/inngest`), never a request-scoped timer. Job **bodies** stay as plain functions in `src/server/events`/`inventory` so they are unit-testable and portable if the scheduler changes; the Inngest function is a thin cron + retry wrapper. Crons: `dispatch-outbox` 1 min, `sweep-reservations` 2 min, `outbox-health` 10 min, all `concurrency: 1`; `on-outbox-dispatched` event consumer, 4 retries. Signature verification on the endpoint when `INNGEST_SIGNING_KEY` is set. | 2026-09-07 | Playbook Phase 6 agent prompt — "never rely on a request process staying alive after the response". |
| D-50 | **Authorised, audited replay** — `replayOutboxAsOwner` = `requireOwner()` then `replayOutboxEvent` (one tx: reset to PENDING/attempts 0/availableAt now + `AdminActivityLog{action:"outbox.replay"}` + resolve `outbox:<id>`). No admin-role (non-owner) or unauthenticated replay path. Runbook §4 has the operator procedure. | 2026-09-07 | Master §8 / AC-10 — "outbox recovery + audited replay". |

| D-53 | **Razorpay crypto is a pure module** (`razorpay-crypto.ts`): `checkoutSignature` = `HMAC_SHA256(order_id\|payment_id, key_secret)`, `webhookSignature` = `HMAC_SHA256(rawBody, webhook_secret)`, constant-time hex compare, plus entity/webhook normalisers. No network, no DB → unit-tested with known vectors. `RazorpayProvider` delegates to it; `FakeRazorpay extends RazorpayProvider` and overrides only the 5 network methods, so tests exercise the real verification code. | 2026-09-07 | Master §8 "Use raw webhook bytes for signature verification"; keeps the security-critical code trivially testable. |
| D-54 | **`PaymentAttempt` is claimed before the provider call** and keyed by a unique `operationKey` (`pay:<orderId>:<seq>`). On a crash between the local claim and `createOrder`, retry reuses the incomplete row (status CREATED, `providerOrderId` null). A duplicate *provider* order (orphaned, unpaid) is accepted as harmless; a duplicate *local* attempt cannot occur. Master's "attach the returned reference safely" is met by reconcile, not by a provider-side idempotency key (Razorpay Orders has none). | 2026-09-07 | Master §7.4. |
| D-55 | **Confirmation requires signature AND server truth**: `verifyPrepaidCheckout` checks the HMAC, then `fetchPayment` and asserts `order_id`, `currency === INR`, and (for a captured payment) `amount === order.totalPaise`. A valid signature with a wrong amount is a **real payment** → order `NEEDS_REVIEW` + one `payment-review:<orderId>` `PAYMENT_REVIEW` task, never a silent failure. `authorized` (not `captured`) → attempt AUTHORIZED, order stays PENDING_PAYMENT, no fulfilment. | 2026-09-07 | Master §8 "Never accept browser success as proof … Authorization alone is insufficient." |
| D-56 | **Settlement is idempotent via `runOnce("settle:<orderId>")`** (Phase 6 `SideEffectExecution`). The checkout callback and the `payment.captured` webhook both route through one `settleOrRecord`; the first to run settles (reuses Phase 5 `settleCapturedPayment` — convert reservations / late-capture reacquire / NEEDS_REVIEW+PAID), the rest are skipped. `attempt.status === "CAPTURED"` short-circuits so a stale `payment.failed` cannot downgrade a paid order. A second distinct `payment.captured` on a settled order → extra CAPTURED `PaymentAttempt` (`pay:<order>:excess:<pid>`, unique on `(provider, providerPaymentId)`) + `payment.excess_capture` + review task; order not re-confirmed. | 2026-09-07 | Master §8 "Prevent duplicate captured attempts from causing duplicate fulfillment; flag excess captures for refund review." |
| D-57 | **Webhook route reads raw bytes** (`Buffer.from(await req.arrayBuffer())`) and hands them to `ingestWebhook` (Phase 6): verify → persist+dedupe on `(provider, externalEventId)` → then process. Bad signature → 401, nothing stored. Persistence failure → 500 (Razorpay redelivers).
